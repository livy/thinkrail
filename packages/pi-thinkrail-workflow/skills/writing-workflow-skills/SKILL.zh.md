# 撰写工作流 skill

> 中文译文，原文见 [`SKILL.md`](./SKILL.md)。英文原文是唯一权威来源，二者不一致时以原文为准。

`packages/pi-thinkrail-workflow` 中工作流 skill 的撰写检查清单。它承载*做什么*；每一个 *why* ——
概念模型、三种角色、下文以“(rule N)”引用的元规则 —— 只住在本目录旁的工作流系统规格
**`skills/SPEC.md`** 里一次。先读那份规格；当本检查清单与那份规格冲突时，规格胜出。

**工作区守卫。** 本检查清单编辑的是 thinkrail 仓库里的 `packages/pi-thinkrail-workflow`。
如果该包不在当前工作区中（一个由 ThinkRail 管理的项目，这些 skill 在那里是一份只读的暂存缓存），
家族就无法从这里扩展：用一行说明这一点并停下 —— 这是外来工作区的终止状态。

## 设计（Design (before writing)）

- [ ] 阅读 `skills/SPEC.md`：概念模型、三种角色、元规则 1–15。
- [ ] 把 skill 限定在一个外部可达的工作流 —— 或对概念而言，限定在一个主题上（规则 1）。
      内部的分叉、分支、阶段与共享尾段都是同级文档，在分叉之前就用文档（或主干）中的选择规则
      规划好；只有当一份文档需要独立可寻址性（一个外部调用方、真正的自触发，或一个直接入口，
      例如 `/skill:` 命令种子）时，它才被提升为自己的 skill —— 绝不只因形态或体量。
- [ ] 选定角色（规则 2）：**路由器**（分类规则 + 交接，别无其他）、**worker**（一个阶段的步骤），
      或**概念**（一个主题的可复用规则/心智模型 —— 没有步骤，没有交接）。
- [ ] 对概念：确认第二个 skill 确实需要它（规则 3）—— 只有单一消费者的参考细节仍是同级文件，
      而不是概念 skill。
- [ ] 选定结尾（规则 6）：路由器以点名接下来运行什么结尾；worker 以固定后继、返回其调用方，
      或一个已宣告的终止状态结尾 —— 内部有分叉的 worker 以点名延续流程的那份同级文档结尾，
      终止状态则在实际结束流程的那份文档中宣告；概念根本没有结尾 —— 它不写结尾章节，控制权直接
      回到其读者。在写正文之前就知道确切的措辞。
- [ ] 如果这次改动重塑了系统本身 —— 一个新角色、一条新元规则、改变的入口模型或拓扑 —— 停下：
      先更新 `skills/SPEC.md`，然后回到这里（规则 13）。

## 撰写（Write）

- [ ] 以动词开头、主动语态、kebab-case 命名该 skill（规则 15）：过程类 skill 用动名词，概念用其
      主题 —— 命名该工作或该洞见，绝不是产物或角色。目录名 = frontmatter 中的 `name`。
- [ ] 创建 `skills/<name>/SKILL.md`，带 frontmatter `name` + `description`。其他什么都不变 ——
      `package.json` 的 `pi.skills` 已经指向 `./skills`。
- [ ] `description` = 仅触发条件，“Use when …”（边界容易混淆时再加一个“Not for …”的否定触发）
      —— 绝不是对步骤的摘要（规则 5）。skill 通过路由触达；自触发的 description 只用于确凿无疑的
      触发条件（规则 4）。
- [ ] 每个文件保持在 ~150 行以内（规则 3）—— `SKILL.md` 主干与每份同级文档皆然。工作流的内部节点
      （分支、阶段、共享尾段）与厚重的参考材料住在 `skills/<name>/` 内的同级文档里，在交接给它们的
      确切步骤中具名；主干承载文档地图，每份内部节点文档以一行契约开头（进入状态、保存什么、
      控制权接下来去哪）。
- [ ] 每件事只说一次（规则 7）：按名交叉引用其他 skill；绝不内联另一个 skill 的步骤，
      绝不强行加载它的文件。
- [ ] 在纪律要紧之处设门禁，并让形式匹配失败模式（规则 11）：纪律违规用禁令 + 红旗，
      输出形态用正向配方。
- [ ] 持久输出进入规格图谱（规则 8）。如果工作流需要临时工作文件 —— 续跑状态、草稿计划 ——
      就宣告它们（规则 9）：在 skill 里点名它们的形态，把它们放进工作区被 gitignore 的
      `.thinkrail/context/`（每个临时文档的家），在工作落地时消费/删除它们，并在清理之前把任何
      持久内容提升进规格。
- [ ] 以点名设计阶段选定的结尾来结束正文（规则 6）—— 概念跳过这一步：没有结尾章节。

## 注册（Register (rule 12)）

- [ ] 在拥有这个新 skill 的路由器里加一条路由行：默认是根路由器
      （`skills/choosing-a-workflow/SKILL.md`），或当该 skill 是某条已路由工作流下的分支时，
      是最近的子路由器（分形路由）。例外（规则 4）：处于任何路由器工作分类之外的 skill ——
      仅自触发的 skill 与概念 skill —— 跳过路由行；这是该 skill 设计上的属性，绝不是体量上的判断，
      并且它改为在 `skills/SPEC.md` 的家族表中被点名，声明其在路由表之外。
- [ ] 在 `skills/SPEC.md` 的 **Workflow family** 表中添加或更新该 skill 的一行，包括它的
      **Routed from** 条目（哪个路由器路由到它 —— 或它位于路由表之外）。
- [ ] 其他任何东西的形态都不应改变 —— 如果变了，回到设计阶段的规则 13。

## 通过使用验证（Verify by use (rule 14 — currently suspended)）

- [ ] 规则 14 今天是已知限制，不是完成门禁（见 `skills/SPEC.md`）。在可行时，仍要让一个真实请求
      流经新增或变更的 skill 并观察它的流动：路由器（或该 description）触发它，正文被遵循，
      结尾按设计触发。对概念而言：某个引用它的 skill（或它的自触发）加载它，它的规则被应用。
- [ ] 无论哪种方式，都要让家族表的那一行保持诚实：在一次运行被观察到之前标记
      `unverified by use`；观察到了就更新该行。

## 红旗 —— Red flags — stop and fix

- `description` 提到了该工作流的任何步骤。
- 名称是名词开头的，或命名的是一个产物/角色而不是工作（规则 15）。
- 路由器或 worker 的正文结尾没有点名后继或终止状态。
- 概念 skill 含有步骤、路由、交接或结尾章节。
- 同样的规则被复制进两个 skill，而不是抽取成一个概念（规则 7）。
- 某个步骤复述了另一个 skill（或 `skills/SPEC.md`）的内容，而不是指向它。
- 一个 skill 之外没有任何东西能触达的内部节点被做成了自己的 skill（或给了 frontmatter）——
  内部节点是同级文档，不是 skill（规则 1）。
- “小到不需要路由行 / 家族表行。” 每个 skill 都要注册（规则 12）；跳过路由行只适用于仅自触发的
  skill 与概念 skill（按规则 4）—— 体量从来不是理由。
- 在没有观察到真实请求流经它的情况下就把某个 skill 称作*已验证* —— 规则 14 作为完成门禁已暂停，
  但未被观察的 skill 仍然是 `unverified by use`，绝不是“已验证”。

## 完成（Done (terminal state)）

本检查清单到此结束 —— 没有后继 skill。完成的含义是：`skills/<name>/SKILL.md` 存在并通过上述检查，
且路由行与家族表行都已就位 —— 该行诚实地标记为 `unverified by use`，直到观察到真实请求流经该
skill 为止（规则 14，目前作为完成门禁处于暂停状态）。
