# syncing.md —— 让 PR 更新到最新

> 中文译文，原文见 [`syncing.md`](./syncing.md)。英文原文是唯一权威来源，二者不一致时以原文为准。

入口：一个已打开的 PR 落后于它的基线，或存在冲突。不保存任何内容。同步保留调用方的完成模式，
在直接进入时默认使用快照模式；控制权随后交给 `checks.md`。

1. `git fetch origin`，然后把分支 rebase 到基线之上 —— 或者，如果该 PR 既有历史风格是基于 merge
   的，就 merge；遵循这个 PR 已经在做的做法。
2. 通过理解双方来解决冲突：在选择之前先读冲突 hunk 的历史（对每一侧 `git log -p`）。
   机械式的“采用我们的版本”正是刚合并进来的工作被悄悄回退的方式。
3. **重新评估验证证据。** 对结果改动应用主干的最终树规则。判断哪些门禁被失效时，要检查冲突解决、
   相关依赖变更，以及触及该改动行为或测试面的基线提交；只有当基线移动得足够大、足以使其失效时，
   才动用完整标准。仅提交祖先关系变化本身并不强制重跑。
4. 如果步骤 3 导致了修复，提交它，并针对新的 head 重复步骤 3。只有当证据覆盖了最终树、且
   `git status --porcelain` 为空时才推送（主干的行动点规则）。rebase 之后用 `--force-with-lease`，
   绝不用裸 `--force`。

红旗：“rebase 过了，所以一切都要重跑”忽略了有效证据；“没有冲突，所以每一个旧结果仍然适用”
忽略了相关的行为或依赖变更。重新评估证据是无条件的；重跑命令则不是。
