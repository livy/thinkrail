# review-comments.md —— 处理意见，绝不盲从

> 中文译文，原文见 [`review-comments.md`](./review-comments.md)。英文原文是唯一权威来源，二者不一致时以原文为准。

入口：一个已打开的 PR 有待处理的评审意见。不保存任何内容。无论是否推送了被接受的修复，默认都是
快照模式。仅当主干明确的远端完成规则选中它时，才保留等待模式。

1. **先通读整个 PR。** 取全部评论讨论串与完整 diff（`gh pr view <n> --comments`、
   `gh api repos/<owner>/<repo>/pulls/<n>/comments --paginate`），然后端到端重读这个 PR 的改动。
   每条意见都对照整个改动来判定，而不只是它引用的那几行。
2. **在碰代码之前，为每条意见给出裁定**：*采纳*（它是对的）、*反驳*（它错了或误读了设计 ——
   说明理由，引用规格或设计），或*澄清*（确实含糊 —— 问评审者或用户）。把裁定汇总起来；
   只要有任一裁定是反驳，就向用户呈现它们。
3. 把被采纳的意见作为正式的改动施加，然后应用主干的最终树验证规则。提交所有内容，如果验证又导致
   一处修复，就重复该规则；只有当证据覆盖了干净的最终树时才推送。**在推送落地之后才回复每个讨论串**：
   改了什么、改在哪里（点名提交），或者反驳的理由。只解决真正处理过的讨论串。

红旗：

- 只修补被引用的那一行，而不读它周围的设计 —— “不要盲从地修它们”是本文档立身的要义。
- 回复“done”，却没有一个已推送、能展示它的提交。
- 悄悄跳过某条意见 —— 每个讨论串都要得到一个答复。
