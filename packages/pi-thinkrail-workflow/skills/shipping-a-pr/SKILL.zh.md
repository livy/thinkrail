# 交付一个 PR

> 中文译文，原文见 [`SKILL.md`](./SKILL.md)。英文原文是唯一权威来源，二者不一致时以原文为准。

PR 生命周期：交付工作区里已完成的工作，维护 PR 的元数据，并在被要求时保持 PR 健康。一个工作流，
六个阶段作为同级文档 —— 从请求点名的那个阶段进入。

## 完成模式（Completion modes）

- **快照模式是默认值**，适用于创建、同步或更新 PR，以及一次性的状态请求。取一份新鲜的检查与
  合并状态快照，按观测到的原样报告 pending/失败/不确定状态，然后停下，既不轮询也不修复无关状态。
  一次推送本身绝不会把模式升级。
- **等待模式需要明确的远端完成请求**：监视或观察检查、排查 CI、等到全绿，或让 PR 达到合并就绪。
  完成的含义是：每项已配置的检查都绿，head 与其基线一致，且 GitHub 报告肯定的合并状态；
  用户请求的草稿按其草稿状态报告，绝不称作合并就绪。没有 CI 的仓库就按其原样报告，绝不悄悄
  算作全绿。

## 观测，绝不假设（Observed, never assumed）—— 适用于每个阶段

Git 与 GitHub 的状态是并发且可变的：基线会移动，CI 会滞后，可合并性是惰性计算的，而本工作流
自己的步骤会弄脏它刚刚检查过的树。四条规则在每个阶段的每一步都成立：

- **在行动点验证。** 一个不可逆的步骤 —— 推送、`gh pr create`、`gh pr edit`、回复某个讨论串、
  宣告完成 —— 在运行之前立即重新检查它所消费的确切状态。早前通过的门禁，不会在它通过之后
  发生的那些变更中存活下来。
- **让验证与最终树绑定。** 在它们覆盖的输入保持不变期间，复用之前的确切结果。在每一次影响代码的
  推送之前，运行项目要求但缺失、或被后续代码、配置、依赖、基线或冲突解决改动所失效的检查。
  如果某个检查、清理或自审又导致了另一处相关编辑，先重新评估并重复，再推送。
- **去取，而不是去记。** 远端状态在需要的那一刻新鲜而完整地读取：编辑正文之前先取当前正文，
  每一次列表都加 `--paginate`，推理基线之前先 `git fetch`。
- **不确定不等于肯定。** 在等待模式下，pending 或仍在计算中的答案（`UNKNOWN` 合并状态、排队的
  检查）会被轮询直到解决；只有从观测到的肯定状态才宣告完成。在快照模式下，把它作为不确定报告，
  而不把该阶段变成一次监视。

## 判定请求（Classify the ask）

| 请求 | 阶段文档 | 默认模式 |
|---|---|---|
| 创建一个 PR —— 工作已完成 | `creating.md` | 快照 |
| 让 PR 更新到最新 / 解决与其基线的冲突 | `syncing.md` | 快照 |
| 更新 PR 的标题或正文 | `body.md` | 快照 |
| 在 PR 上添加或刷新截图 | `screenshots.md` | 快照 |
| 一次性报告当前的检查 / 合并状态 | `checks.md` | 快照 |
| 监视 CI / 排查或修复失败的检查 | `checks.md` | 等待 |
| 处理评审意见 | `review-comments.md` | 快照 |

**阅读并遵循所选的那份阶段文档** —— 门禁与机制只住在那里；绝不凭这份主干的摘要去运行某个阶段。
把上文选定的完成模式带进那份文档；后续的推送不会改变它。一个复合请求（“rebase、验证并创建 PR”）
是一条流程：从点名的最早阶段开始；各文档会自行向前串联。如果工作本身尚未完成 —— 请求在交付之前
捆入了新的设计或实现 —— 那部分不属于本工作流；先按 choosing-a-workflow 路由它，等它落地后再回到
这里。

## 工作文件（Working files）

本工作流使用的临时文件，全部位于工作区中被 gitignore 的 `.thinkrail/context/` 下：

- `pr-body.md` —— PR 正文草稿；始终通过 `--body-file` 传入，绝不用内联。
- `pr-shots/` —— 待附上的前后对比截图，先暂存在这里。

制作它们的那个阶段完成时，两者都会被删除（截图在用户手工上传期间保留 —— 见 `screenshots.md`）。

## 结尾（Ending）

每个阶段都以上文选定的完成模式经由 `checks.md` 结束。
