# 撰写规格

> 中文译文，原文见 [`SKILL.md`](./SKILL.md)。英文原文是唯一权威来源，二者不一致时以原文为准。

工作流家族为每个工作流产出的规格所持有的共享标准：**短、诚实、不脱轨**。流程类 skill 在起草或
修订规格的步骤上点名这一概念；*起草什么*与*何时起草*仍由引用它的 skill 决定。图谱机制 ——
frontmatter、链接种类、`spec_*` 工具 —— 是规格图谱 skill 的地盘；本概念承载的是家族在其之上
持有的质量线，也是家族关于规格与规格图谱的规则不断累积的地方。

## 短（Short）

- 小到能一口气读完。目标是信号，而不是完备性。
- 解释意图，而不是清点清单：它是干什么用的、拥有什么、边界在哪里 —— 绝不是文件罗列或对代码的
  复述。

## 诚实（Honest）

- 只出现已经确定的内容。绝不用 `[TBD]` 或占位章节来填充 —— 尚未确定的章节就干脆还不存在。
- 任何属于推断而非确认的内容，都在它所在之处就地标记为未确认。
- 新建的和推断的规格都是 `status: draft`，直到用户评审过它们 —— 翻出 `draft` 取决于用户的评审，
  绝不是起草 agent 自己的判断。被评审过的长期规格走向 `active`，绝不是 `done`：它保持有效，
  并随项目一起演进。

## 不脱轨（On-rails）

- 信号足够高，使未来的 agent（或人）能直接落到那些决策上，不必重新推导。
- 规格是理由的*唯一*归宿：决策、不变量、权衡与缺陷复盘都记录在这里，绝不作为代码注释 ——
  在代码里找到的一段理由，是需要提升进所属规格的内容，最多留下一行指针，用在误改会悄悄弄坏
  某处的地方。
- 每件事只说一次：用 `id` 链接而不是复述；同级模块*之间*的依赖边住在父模块的规格里，
  而不是每个叶子里。
- 每个*真正的*边界一份规格 —— 不是每个目录一份，也不是每个文件一份。

## 目标文档描述产品，而不是计划（The goal doc describes the product, not a plan）

`goal-and-requirements` 是关于产品是什么、为什么的活记录：它的目标、问题、受众、能力与非目标，
外加任何持久的原则。

- 不写版本、发布、阶段、MVP/v1/v2 切分，或“以后再说”的清单。排序不是规格的职责：
  被砍出范围的想法交还给用户，由他们在自己规划工作的地方跟踪，绝不写进文档。
- **能力（Capabilities）** 陈述产品做什么；对一个新项目而言，则是它最小可用的首次构建会做什么。
- **非目标（Non-goals）** 只装以决策排出的内容。既未列出也未排出的东西是开放的，不是被禁止的。
- 它随产品一起演进：新增一项能力或推翻某条原则的改动，在同一次改动中更新目标文档。
