# 修订规格 —— brainstorming 的共享尾段

> 中文译文，原文见 [`amending-specs.md`](./amending-specs.md)。英文原文是唯一权威来源，二者不一致时以原文为准。

入口：已接受的改动已构建并验证（主干步骤 8）。保存：长期规格图谱。
结束：该工作流。

只有当每一处改动都落进规格时，规格才保持为唯一权威来源。这是你的工作，不是一轮审批：自己动手，
让用户在 Changes 评审中看到结果。先读 **writing-specs** 概念 skill —— 它的标准适用于这里的
每一次编辑。

1. **用规格的语言找出改了什么** —— 依据 task-spec 与实际 diff，而不是计划：
   - 目标文档，当新增或移除了一项能力，或推翻了某条原则时；
   - `architecture.md`，当拓扑、某个跨模块决策或某个仓库级不变量发生移动时；
   - 所属模块或子模块的 `SPEC.md`，针对职责、边界、契约、决策或已知限制 —— 以及为真正全新的
     模块新增一份规格；
   - 对于被归类为 silent 或 wrong 的缺陷，是那份本应写明预期行为的规格。
2. **自上而下修订** —— 目标 → 架构 → 模块 —— 不必请用户批准清单或编辑。用 `spec_create` 新建
   规格，用 `spec_update` 改 frontmatter，用 `edit` 改正文。把决策以及代码无法呈现的 *why* 写一次，
   写在拥有它们的规格里；其余用 `id` 链接。未确认的假设在它所在之处标记为未确认。
3. **对照现实检查。** 每份修订后的规格与已构建的内容一致，而不是与计划一致；你改动过的规格彼此
   不矛盾，也不会把同一个术语用于两种含义。运行 `spec_validate` 并修复它报告的问题。
4. **没有任何长期内容改变？**（一个被归类为 right 的缺陷，一处规格已经描述的改动。）那就不要做
   任何编辑 —— 绝不为了显示有活动而虚构内容。
5. **用一两行报告：** 哪些规格变了，按名称列出，以及留在其中的任何未确认假设。不要逐文件叙述。
6. **退役 task-spec** —— 一旦它的长期内容已进入树中，就删除它。

## 结尾（Ending）

这个工作流到此结束。PR 生命周期工作，如被请求，则另行进入 **shipping-a-pr**。
