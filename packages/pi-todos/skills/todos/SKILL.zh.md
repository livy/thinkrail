# 聊天 TODO 计划

> 中文译文，原文见 [`SKILL.md`](./SKILL.md)。英文原文是唯一权威来源，二者不一致时以原文为准。

## 它是什么（What it is）

- 一份**限定在本聊天内**的计划 —— 你为这个对话承担的任务。在 Todo 面板中展示给用户；
  随会话存在（不提交进仓库）。
- **分组 = 任务，条目 = 步骤。** 一个用户请求 = 一个分组；它的标题是*结果*（“修复登录重定向”），
  而不是过程。里面的步骤就是条目 —— 每条有一个**标题**、一个**状态**
  （`pending` → `in_progress` → `done`），以及一个可选的**注记**。注记是**面向 agent 的工作细节**
  —— 人的默认计划视图显示标题 + 状态，把注记藏在一个展开区之后 —— 所以它正是你自己的跟踪、
  提醒与完成标准所住之处（例如“登录 e2e 全绿”），绝不是用户为了跟上进度而必须读的地方。
  任务自身的状态从不存储 —— 它由它的步骤派生。
- **松散条目是共享的原始输入队列 —— 而且它们位于计划的末尾。** 双方都往那里写：用户从 UI 添加，
  你也可以用 `todo_add`（不带 `group`、不带 `after`）投下一条未处理的注记。松散条目是*工作之前*
  的东西 —— 原始的种子与半成形的请求，绝不是你即将执行的某个步骤。`todo_list` 有意把它们渲染在
  **最后**，排在每一个分组之后：任务中途添加的条目排在*你当前工作之后*。所以**在拿起一条松散条目
  之前，先完成（或恢复）你手上的任务** —— 不要跳到刚添加的条目上、把你进行中的步骤丢下。
- **在你把一条松散条目纳入工作的那一刻就提升它 —— 用 `todo_promote <loose-id>`。** 一次原子调用：
  该松散条目从队列中消失，一个分组继承它的 id 与标题。没有重复窗口，没有 `todo_remove` 的花招，
  而且如果会话紧接着就死了，计划仍然诚实地把用户的请求显示为它自己的分组。然后用
  `todo_add group:"<same title>"` 加上第一个实质步骤并把它翻成 `in_progress` —— 即便只是一句
  “调查这个请求并勾画计划”也是真实的步骤，于是用户从第一拍就能看到她的任务正在被处理。只有当用户的
  措辞无法作为分组标题时，才给 `todo_promote` 传 `title:`；否则原样保留。体量不重要：一条 pending
  的松散条目已经在计划里了，所以即便是 1–2 步的条目也会变成一个小分组。不要为其他任何理由改写或
  丢弃松散条目，也绝不要为用户来源的松散条目用 `todo_add group:` + `todo_remove` 手工造一个分组
  —— 那正是 `todo_promote` 取代的旧两步花招。
- 它是**共享且实时的**：由你维护，而**用户会在你工作期间编辑它** —— 添加任务、移除他们已放弃的
  任务。存储的列表才是**唯一权威来源**；你记住的只是一份快照。**重新读它（`todo_list`）**来保持
  同步，不要相信你对它的记忆。
- 它是**用户的状态窗口** —— 用户如何一眼跟上正在发生什么，而不必读聊天记录。简短、具体的步骤标题；
  状态始终最新。

## 粒度（Granularity）

| 请求的大小 | 计划中的形态 |
| --- | --- |
| 1–2 个执行步骤，包括一次性的回答、检查或编辑 | 除非用户要求，否则不列计划 |
| 3–7 个实质步骤 | 一个分组 |
| 超过 ~10 个步骤 | 那些是任务，不是步骤 —— 拆成多个分组 |

步骤是**可验证的**，且大约与一次提交同尺寸：“一边做一边容易打勾”，而不是“阶段 1”。

**一个步骤是实质的、对人而言有意义的结果 —— 不是你的记账。** 计划是用户的状态窗口，所以每个步骤
都必须是*用户*在意看到完成的事。只让你自己保持方向的流程/元信息絮叨不是步骤：“制订计划”、
“读文件”、“想想方案”、“审查我的改动” —— 不要为这些铸造条目。把计划限制在真实、可核查的结果上；
你需要的任何工作记忆放进步骤的 `note`（面向 agent），而不是单独作为一个条目。

**每个字段回答一个问题，用一种形态 —— 不要让它们彼此模糊：** **标题**是这一步做什么（祈使式，
关于改动/结果，而不是过程）；**`note`** 是你私密的工作细节；**`summary`** 是改了什么以及*为什么*
（它绝不能复述标题 —— 而是补上标题无法呈现的决策或约束）；**`verification`** 是如何证明的，
采用规范化形态 `check → result`（或诚实的“未验证”）。

## 如何使用它（Working with it）

1. **发布一份有用的计划，而不是推测性的计划。** 一旦任务被理解到足以识别出至少三个实质执行步骤，
   或足以满足用户对计划的明确请求，就用 `todo_write`，每个任务一个分组。澄清问题可以先问，
   当它们的答案会改变计划时。在执行之前发布计划，然后只在工作确实发生变化时才细化它。
2. **严格按顺序处理任务，一次一个步骤：**
   - 开始某一步时把它翻成 `in_progress`，完成时翻成 `done`。开始新的一步会自动把任何其他
     `in_progress` 的步骤退回 `pending` —— 所以先完成（标记 `done`）再往下走，否则上一个步骤会
     可见地掉回未完成。
   - 当前分组还有未完成步骤时，不要开始下一个分组。唯一的例外：一个确实**被阻塞**的任务 ——
     把原因记在步骤的 `note` 里，告诉用户，然后继续下一个分组。
   - 在选择每个下一个条目之前、在用户输入之后、在完成之前，用 `todo_list` 重新读一遍。
     新的松散条目追加在末尾 —— 在正在进行的步骤之后再把它们（提升后）接上。如果你计划过的某个
     条目不见了，是用户把它删了：跳过它，不要重新添加。
   - 工具结果会帮你：在一个 `done` 之后它们会点名该任务的下一个步骤；当没有任何东西处于
     `in_progress` 时它们会提醒你翻转你正在做的那个步骤。照这些提示行事。
3. **会话中途一个符合条件的新请求得到一个新分组**（每次一个步骤用带 `group:` 的 `todo_add`，
   或多个步骤就多次调用）。一个普通的 1–2 步聊天请求只有用户明确要求计划时才得到那个分组；
   否则先完成进行中的任务，再直接处理它。当那个短请求已经是一条 pending 的松散条目时，
   改为把它提升成自己的分组。绝不要把新请求的步骤混进当前分组。**在当前任务内部发现的某个步骤**
   用 `todo_add after: <current step id>` 插入；锚定在松散条目上会被拒绝。不要为此用 `todo_write`
   重建计划。
4. **在完成之前对账。** 在最终交接之前再读一次 `todo_list`。如果还有未完成的步骤，要么做掉它们，
   要么清楚说明还剩什么以及为什么。

## 完成摘要 —— Completion summaries (the review trail)

用户从摘要 + diff 来评审你的工作。diff 展示*什么*；摘要必须承载 diff 无法展示的一切 ——
意图、决策，以及关于验证的诚实交代。为评审者写它，而不是为自己写。

- **改动了代码的步骤在标记 done 时同时得到 summary 与 verification** —— 在设置 `status: done` 的
  同一次 `todo_update` 调用里把两者都传上。`summary` 是**结构化写出的 Markdown**（一句简短的
  引导句 + 有多个部分时用项目符号列表），覆盖**改了什么**与**为什么** —— 尤其是 diff 中看不见的
  决策（一个被否决的替代方案、一个你绕过的约束）—— 而不是一段连写的流水句。
  纯研究/分析/验证、没有产生代码改动的步骤则两者都不需要。
- **验证是它自己的字段，有名有姓，绝不空口宣称。** 把 `verification` 传成一条或多条检查，采用
  规范化形态 `check → result` —— 你实际运行的那条检查及其结果（“`bun test src/todos` → 34 pass”、
  “typecheck → green”）—— 或者诚实的**“未验证”**。它在计划页上渲染为 **Markdown**，所以当你跑了
  多项检查时，把它们写成**项目符号列表**（一行一条 `- check → result`），而不是挤在一行里用 `;`
  隔开的流水句；单条检查保持一行。UI 把它显示为评审卡片上的状态徽章，所以一句含糊或缺失的话一眼
  就能看出来。绝不要为你没有运行的测试写“tests pass”。而且绝不要靠削弱一项检查来让它通过 ——
  如果你在该步骤中改动、跳过或删除了某个测试，摘要必须明确说明：一个自己发现了这件事的评审者，
  会停止信任其他每一份摘要。
- **改动了代码的步骤还会得到一个 `commitSubject`。** 宿主在用户的分支上提交该步骤的增量，并把这一行
  原样用作提交标题，所以把它写成一条**提交消息，而不是计划步骤**：关于*改动*的一行祈使句，
  并遵循**本仓库既有的风格** —— 运行 `git log --oneline -20`，照着看到的写（Conventional Commits ⇒
  `type(scope): subject`；散文式标题的仓库 ⇒ 散文）。它必须能原样推送：没有 `todo:` 前缀、
  没有条目 id、没有工具署名。省略它，宿主就退回使用步骤标题，那在 `git log` 里读起来像一个计划
  步骤 —— 所以别指望那个兜底。
- **披露范围漂移。** 任何越出该步骤自身请求的触碰 —— 一处相邻的重构、一次顺手改名、一个新依赖 ——
  都写进摘要（“also touched X because Y”）。agent 改动的标志性失败是解决被问的问题*再加上*邻居；
  未披露的额外内容正是评审者最不信任的东西。
- **指向风险。** 当改动中有一部分最值得评审者细看 —— 一处契约/API 变更、棘手的并发、你最没把握的
  地方 —— 用一个从句点名它（“最需细看：回滚路径”）。
- **当最后一个未完成条目翻成 done 时，用 `todo_plan_summary` 写出整体计划摘要**（`todo_update` 的
  结果恰好在那一刻提示你）：这是一份跨所有任务的交接注记，而不是步骤清单。它是**累积的 —— 覆盖
  整个计划中做过的所有事情**，而不只是最后一步。当计划新增了工作并再次完成时，早先那次完成写下的
  摘要仍在那里（done 翻转的提示会把它呈现出来）：**扩展那段文字 —— 把之前每一点都带过来，再加上
  新的工作 —— 绝不要把它重写成只剩最近的步骤。**

  **始终用与 PR 正文相同的形态写计划摘要** —— 宿主把 `plan.summary` 原样喂给 `renderPrBody`，
  所以形态良好的摘要无需第二遍就是 PR 就绪的。三个 H2 章节，按此顺序：

  - `## Summary` —— 用散文写做了什么以及为什么。意图、用户可见的结果、diff 无法展示的决策与权衡
    （一个被否决的替代方案、一个你绕过的约束），以及任何相关 issue 行（`Closes #NNN`）。
    这是自动渲染的 `## Plan` 无法代为发声的那一节。
  - `## Changes` —— 在计划层面交付了什么：迁移、范围之外的触碰、新增或移除的依赖、重命名，
    任何评审者应当注意、超出逐步清单的东西。不要复述步骤标题 —— 自动渲染的 `## Plan` 一节已经
    带着它们以及各自的 `summary` 行；`## Changes` 是给那些只在计划尺度上才有意义的跨领域注记用的。
  - `## Testing` —— 超出逐步检查所做的端到端验证（例如最后跑一次 `bun run e2e`、对集成后的改动做
    一次冒烟运行），每行采用规范化形态 `check → result`，写成项目符号列表，或诚实的 `not verified`。
    逐步的 `verification` 行留在各自的步骤上，不在这里重复。

  把任何未完成或推迟的内容放进匹配的章节（通常是 `## Changes`）—— 一处遗漏会被读成“没有剩下什么”，
  所以如果确实有，就写出来。在有助于扫读的地方使用 `**加粗**`、列表与 `code`。逐条的 `summary` 也
  渲染为 Markdown —— 一两句紧凑的话，只有确实有多个部分时才用项目符号。让每个展示面都可扫读，
  绝不要一整面文字墙。
- **修复请求会重新打开同一个条目。** 当用户要求修复某个已评审的步骤时（你会收到原始步骤、它的摘要、
  它的变更集，以及他们的反馈），把**那个确切的条目**（按 id）翻回 `in_progress`，做这次修复，
  并用一份**全新的摘要**与一个**全新的 `commitSubject`** 把它标记为 `done`，描述这次修复 ——
  是修复，而不是原始工作（用户只重新评审新的增量，而修订作为它自己的提交落地）。重新打开会清空先前的
  值，所以要再次提供两者。绝不要为一次修复新开条目 —— 修订必须挂到它所修订的那个步骤上。

## 不变量（Invariants）

- **done 会留下。** 完成一个步骤 = `todo_update` → `done`。**绝不删除一个 done 条目** ——
  那是用户的历史。`todo_remove` 只在用户明确要求丢弃某项时使用 —— 你纳入工作的用户松散条目由
  `todo_promote` 消费，而不是手工删除。
- **外科式编辑。** 在首个计划之后，单处改动优先用 `todo_update` / `todo_add`（它们只动一个条目）
  —— 比重述整份计划更省。`todo_write` 是**对账**（它不是破坏性替换）：它按分组 + 步骤标题把你写下的
  步骤与既有条目匹配，并保留它们的状态/摘要/id，所以重新规划是安全且无损的 —— 当你确实在重构时
  才用它，不要为了挪动一个条目而用。状态只通过 `todo_update` 前进；你在 `todo_write` 里对已存在的
  步骤设置的 `status` 会被忽略。
- **尊重用户的编辑。** 列表是共享的；把用户的添加当作新请求，把他们的移除当作取消。松散条目是共享
  队列 —— 你处理它们时提升它们，但重新规划时不要改写或丢弃它们。（`todo_write` 从不碰松散条目，
  并保留 done 条目；但要在一次重新规划中保持步骤标题稳定 —— 一个被改写的标题会被读成新步骤，
  于是旧步骤的进展不会延续。）

## 工具（Tools）

- `todo_list` —— 读取当前计划（唯一权威来源；重新读取以捕捉用户的编辑）。
- `todo_add` —— 添加一个步骤（放进某个 `group`、`after` 某个既有步骤，或两者都省略时作为松散条目；
  其余部分不动）。
- `todo_update` —— 推进一个步骤（开始时 `in_progress`，完成时 `done` —— 当该步骤改动了代码时带上
  一个 `summary`；done 会留下）。
- `todo_promote` —— 一次原子调用把一条松散条目变成它自己的一个分组（同一个 id、同一个标题）；
  用户来源的松散请求就是这样进入执行的。
- `todo_remove` —— 删除一个条目（只在用户要求时 —— 被提升的松散条目已经消失，`todo_promote`
  已经消费了它）。
- `todo_write` —— 铺开或对账计划（仅分组 —— 每个任务一个；按标题匹配步骤并保留它们的进展；
  单处改动优先用 `todo_add`/`todo_update`）。
- `todo_plan_summary` —— 最后一个条目完成之后：对这份计划达成了什么做一段简短的整体摘要。
