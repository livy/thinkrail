# 规格图谱 core（不含 pi 的模型）

> 中文译文，原文见 [`SPEC.md`](./SPEC.md)。英文原文是唯一权威来源，二者不一致时以原文为准。

## 职责（Responsibility）

不含 pi 的规格模型：is-a-spec 规则、frontmatter 的解析/序列化与就地编辑（经由 `yaml` 库，
链接/元数据列表内联）、推导图谱（父树 + `depends-on`/`references`/`implements` DAG + 反向边）、
按需的内存读取索引、带元数据过滤的内容 grep、有界图谱切片，以及结构校验。它**不导入任何
`@earendil-works/*`**，因此可以单独做单元测试（`core/core.test.ts`）。

## 边界（Boundary）

- **拥有：** 上述一切。文件系统是事实来源；模型是推导的、在内存中的、只读的 ——
  重新校验机制住在 `module-spec-graph`（*Derived read index*）中。
- **公开接口：** `index.ts` **barrel**。`tools/` 只通过它导入模型，绝不直接导入叶子文件。
  barrel 约束的是*消费者*；模块自己的测试（`core/core.test.ts`）可以直连一个叶子文件，
  以触达刻意非公开的辅助函数 —— `store.ts` 中的纯路径守卫、段解析器与 glob 顺序比较器，
  它们在不动文件系统的前提下固定 `resolveSpecPath` 与 glob 顺序。
- **允许的依赖：** `yaml`；Node 内置模块。
- **禁止：** 任何 `@earendil-works/*`（这正是让 `core/` 保持隔离且可单测的东西）与任何
  `@thinkrail/*` 包。

## 叶子与依赖图（Leaves & the dependency graph）

无环且单向：`parse` 是根，`graph` 建立在它之上，而 `query`/`validate`/`store` 建立在 `graph` 之上。
barrel 重新导出各叶子，不添加任何逻辑。

| leaf | owns | depends on |
| --- | --- | --- |
| `parse.ts` | 文件 → `{ frontmatter, body }`；is-a-spec 规则；frontmatter 解析（有损的读取方言）+ 序列化；`updateFrontmatterText` 无损就地编辑；`FIELDS` 字段注册表与有限词汇元组 | — |
| `graph.ts` | 文件 → 节点 + 边（父树、DAG + 反向）；重复 id 跟踪 | `parse` |
| `query.ts` | 带元数据过滤的内容 grep；有界图谱切片 | `parse`、`graph` |
| `validate.ts` | 悬空链接、重复 id、父环 | `parse`、`graph` |
| `store.ts` | `SpecIndex`：按需的 fs glob + 逐文件解析缓存 + 记忆化的图谱（`core/index` 模块）；可索引路径规则（`resolveSpecPath`） | `parse`、`graph`、`query` |

## 不变量（Invariants）

- `core/` 之下任何地方都没有 `@earendil-works/*` 导入。
- grep 分页按源码顺序跳过从零开始的匹配偏移，并且只在还存在另一个匹配时返回续页。
  调用方既可限制格式化后的字节数，也可限制条数；一个超大的首个匹配会被接纳，
  以便工具层把它保存在上下文之外，而不是让分页卡住。核心没有以 Pi 为尺度的默认字节策略，
  也不拥有输出文件。
- `buildGraph` 是纯的（同样的输入 → 同样的输出）；索引按 `(mtimeMs, size)` 重新校验每个文件，
  记忆化图谱，且永不提供陈旧的图谱。
- glob **首先**把每个目录的条目过滤到遍历候选 —— 未被忽略的目录，加上 `.md` 文件 ——
  然后才规范化并排序它们，因此一个塞满无关条目的目录，其每次读取扫描的代价不超过丢弃它们的那一趟。
- 那个顺序是**全序**：候选项按**经 NFC 规范化**的名称比较，并以原名的码元作为决胜。
  因此规格顺序 —— 因而哪个文件赢得重复的 `id` —— 在每个文件系统上都相同：
  不是 `readdir` 碰巧返回的顺序，不是在会返回分解（NFD）名称的文件系统上的另一种答案，
  也不是对两个规范等价的拼写（预组合的 `é` 与 `e\u0301`）再次采用 `readdir` 的顺序 ——
  它们共享同一个 NFC 键，否则就会被留在某个稳定排序恰好找到的位置。
  目录与 `.md` 文件留在**同一个**候选列表里，因此子目录在其同级文件之间的位置被下钻，
  而不是排在它们全部之前或之后，规格序列从头到尾都是按名称排序的。先过滤后排序的重写
  **保留**了这一点，并没有引入它；测试之所以存在，是因为两个独立列表是显而易见会去采用的形态，
  而它会静默移动重复 `id` 的胜者。
- 出现重复 `id` 时，该顺序中的第一个文件赢得节点槽位；重复集合被记录下来供 `validate` 使用。
- `resolveSpecPath` 是“索引是否可能看到这条路径？”的唯一答案，并且它用**规范相对路径**作答，
  因此调用方永不可能报告一个索引不会产生的身份。它要求：根相对、在根之内、`.md`、
  在被忽略目录之外、根存在，且根之下的任何组件处都没有符号链接 —— 逐组件用 `lstat` 检查，
  悬空链接也算，因为 glob 从不下钻符号链接。在 Windows 上，含冒号的路径在规范化之前就被拒绝：
  这同时关掉了驱动器相对路径（`C:..\\outside.md`，`isAbsolute` 不认它）与 NTFS 备用数据流
  （`file:SPEC.md`，`readdir` 看不见它）。任何在规范化后仍然存活的 `..` 段也被拒绝，
  且规范的绝对结果必须通过最后一次 `relative(root, target)` 包含性检查。这些重叠的门禁是有意的：
  路径语法、规范化与逐组件规范化不得能够互相削弱。可移植的 `win32` 算术测试在每个宿主上固定住这道
  逃生口；Windows CI lane 还会原生运行本包的测试，包括 `resolveSpecPath` 与 `spec_create` 的集成。
  符号链接规则正是字符串检查与 `realpath` 比较都会漏掉的东西：一个链接无论离开项目、落进被忽略的
  目录，还是指回一个已被索引的目录，都被拒绝，因为在每种情形下它所创建的文件对其他每个规格工具都
  不可见。
- `resolveSpecPath` 在判断或报告每个组件之前，先把该组件规范化到其**磁盘上的拼写**。
  一个字节已经匹配其父目录某个条目的组件按所写采纳；一个在此文件系统上*能够*解析、却不与任何条目
  逐字节匹配的组件 —— 不区分大小写或做 Unicode 折叠的文件系统 —— 成为在
  `normalize("NFC").toLowerCase()` 下与之相等的那个父条目。零个或两个这样的条目是**错误**：
  它失败关闭而不是猜一个身份。规范化在第一个无法解析的组件处停止，其余部分保留调用方的拼写，
  因为在区分大小写的文件系统上，一个位于既有 `docs/` 旁边的新 `Docs/` 确实是 glob 会看到的新目录。
  `rel` 与 `abs` 由那些规范段拼装，绝不来自词法拼写。正是词法的 `rel` 让 `NODE_MODULES/SPEC.md`
  在不区分大小写的文件系统上报告了一个 glob 永不产生的身份，而写入实际落在了 `node_modules/` 里。
  `.md` 规则被判断两次，一次在调用方的字符串上，一次在规范的 `rel` 上，因为一个规范化为
  `SPEC.MD` 的叶子是逐字节精确的 glob 永不索引的文件。存在性用 `lstat` 探测，
  因此悬空符号链接算作能够解析，并仍会到达上面的符号链接拒绝。
  规范化读取的是**父目录**的列表，因此每个存在的父目录都被列举 —— 不只是那些其组件存在的 ——
  而一个存在却无法列举的父目录是**错误**，绝不是空列表。那次 `readdir` 正是 glob 在此处所做的调用：
  解析器无法列举的目录，就是 glob 会放弃的目录，因此写在其下的规格会因与 `node_modules` 中的规格
  相同的理由而不可见。
- **写路径过度拒绝；读路径保持精确。** `resolveSpecPath` 在每个组件经 `normalize("NFC").toLowerCase()`
  折叠后的形式上匹配 `IGNORED_DIRS`，因此它拒绝任何拼写的 `NODE_MODULES/SPEC.md`；
  glob 仍按逐字节精确的 `readdir` 名称匹配。这两种错误的体量并不相同。拒绝过多的解析器给调用方一个
  它可以据此行动的 reason；跳过过多的 glob 会把一个人真的命名为 `Build/` 的目录从索引里丢掉，
  且毫无迹象。仅靠规范化到不了写路径，因为它只为已经存在的组件说话：在一个 `node_modules`
  尚未安装的项目上，`NODE_MODULES/SPEC.md` 曾成功解析、在不区分大小写的文件系统上创建了真正的
  `node_modules`，并把其下每个依赖都交给 glob 去索引。把 glob 也折叠对此毫无帮助 ——
  已安装的 `node_modules` 在磁盘上就是小写，精确检查已经跳过它 —— 却要付出 `Build/` 那个情形，
  因此 glob 保持精确。折叠完全触及不到的是：由 pi 自己的 `write` 写进 `NODE_MODULES/` 的规格，
  永不经过 `resolveSpecPath`。
- `SpecNode.type` 保持 `string`：读取模型索引磁盘上的任何东西，因此它容忍任何 `type`；
  `SPEC_TYPES` 词表只约束 `spec_create` 的撰写接口，永不约束图谱。
- 有限词表（`SPEC_TYPES`、`SPEC_STATUSES`、`SLICE_DIRECTIONS`、`LINK_KINDS`、`IDENTITY_FIELDS`）
  与 frontmatter 字段名（`FIELDS` 注册表）都是单一来源的 `as const` —— 没有重复的字面量列表，
  因此一次重命名是一行改动。`core/` 保持不依赖 typebox；只有 `tools/` 把元组包进 `StringEnum`。
- 读取把 frontmatter 强制到一种标量/字符串数组方言（有损 —— 嵌套映射与注释被丢弃），
  这对推导模型来说足够。写路径（`updateFrontmatterText`）是**无损**的：它就地把一个活的 `yaml`
  Document 变更，因此未被触碰的字段保持其顺序，任何注释/嵌套值都存活下来。字段顺序**被保留、
  永不重排** —— `FIELD_ORDER` 只是 `spec_create` 构建*新* frontmatter 时所用的顺序。
  对围栏内部行做的 `\r` 剥离，是让以 CRLF 撰写的文件得以解析的东西。
- 写路径**只重写 frontmatter 块**：正文被逐字节拼回，前导 BOM 被放回，而施加到被重写块的换行符
  读自 frontmatter 自己的第一个换行（LF 或 CRLF）。从正文不推断任何东西 —— 一个散文恰好混用换行符
  的文件保留它原有的每一个散文字节，这正是“`spec_update` 永不编辑散文”在字节层面、
  而不只是在字段层面成立的原因。
- 读路径以同样的义务反向承担：`grepSpecs` 按 `\n` 切分，在匹配前丢掉行尾的 `\r` 与前导 BOM，
  因此一个锚定模式在 LF 规格、CRLF 规格与带 BOM 前缀的规格上表现一致 ——
  否则 BOM 会把第 1 行从每个 `^` 模式中隐藏起来。
