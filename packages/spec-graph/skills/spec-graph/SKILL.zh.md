# 规格图谱

> 中文译文，原文见 [`SKILL.md`](./SKILL.md)。英文原文是唯一权威来源，二者不一致时以原文为准。

## 规格是唯一权威来源（Specs are the ground truth）

- 规格描述代码背后的架构、决策、契约与边界 —— 那些仅凭代码无法揭示的意图。把它们当作权威。
- **当所属规格管辖这项工作时，就去查阅它。** 当工作依赖、检查、解释或可能改变某个已记录的边界、
  契约、不变量、行为或架构决策时，用 `spec_grep` / `spec_get` / `spec_graph` 找到适用的记录并对齐
  它。如果某处改动与已记录的决策矛盾，要把它暴露出来并加以调和，而不是悄悄背离。
- **让查阅保持有比例。** 规格是决策与边界的地图；代码确认实现。一处局部修复、解释或检查若不改变
  任何已记录的决策，可以只检视它需要的文件，而不必读无关的规格。
- **让它们保持诚实。** 移动或模糊边界、或推翻某个决策的改动，要在同一次改动中更新规格。与代码
  漂离的规格就不再是权威来源。

## 规格是什么（What a spec is）

- 一份持久、声明性的文档。它陈述世界当前的样貌 —— 代码背后的意图、决策、契约与边界 ——
  而不是计划、任务、阶段或一段工作历程。
- 简洁可读。它捕捉*代码中不显然*的东西；它绝不复述代码。
- 标准：读相关规格就应当足以理解一个区域，并构思出一项改进它的任务。

### 保持规格精简（Keep specs lean）

- **解释意图，而不是清点清单。** 描述一个模块是干什么用的、拥有什么、边界在哪里 —— 而不是一份
  逐文件的目录逐字转录。读者能看到文件；规格存在的意义是那些文件*没有说*的东西。
- **记录要紧的边。** 写明模块的边界（允许 / 禁止的依赖）以及其子模块之间的依赖边。只有当某个部件的
  角色或其边无法从名称看出时，才列出它 —— 例如，一张承载真实依赖 DAG 的小表值得存在；
  一张只是把 `foo.ts` 与“foo 工具”配对的表是噪音，改用一句话说明。
- **每件事只说一次。** 一个事实只住在一份规格里；其他规格用 `id` 链接它，而不是复述它。
  如果某段文字正在规格之间被复制，就把它移到拥有该概念的规格里并指向它。重复的散文会漂移，
  并变成矛盾。
- **更偏好散文而非穷举表格**，并砍掉任何只是在改写代码、文件名或同级规格的内容。

## 图谱（The graph）

- `parent` 链接构成一个镜像代码结构的层级：一份 `SPEC.md` 坐在它所描述的模块旁边（分形 —— 一个包与
  它的每个子目录各有一份），根文档则坐在仓库根目录。
- `depends-on`、`references` 与 `implements` 构成一个横跨这棵树的依赖层。

## Frontmatter

- 必需：`id`（一个唯一的 slug）、`type`、`title`。
- 可选：`status`（生命周期）、`parent`（单个链接）、`depends-on` / `references` / `implements`
  （链接列表）、`covers`、`tags`。
- 当一份文件的 frontmatter 带有 `id` 与 `type` 时，它就是一份规格。
- `status` 跟踪规格的生命周期：`draft`（正在撰写）→ `active`（生效），然后是 `stale`
  （正与代码漂离）、`done` 或 `deprecated`。它是可选的，但随着规格定型或老化要保持其最新。
- 类型：
  - `goal-and-requirements` —— 产品目标与范围；图谱的根。
  - `architecture-design` —— 系统级拓扑、跨领域决策与不变量。
  - `module-design` —— 一个包或模块的职责与边界。
  - `submodule-design` —— 同上，针对包内的目录级模块。
  - `task-spec` —— 一件工作的临时工作文档；不持久，工作落地后即被移除。

## 工具（Tools）

读取：

- `spec_grep` —— 在规格内搜索（内容，可用元数据过滤器收窄）。
- `spec_get` —— 一份规格的 frontmatter、它解析后的链接，以及它的路径。用普通的 `read` 工具按该路径
  读取正文。
- `spec_graph` —— 图谱的一个有界切片：一棵子树、祖先，或某个节点的邻居，可指定深度。

管理：

- `spec_create` —— 一份新规格，带脚手架化的 frontmatter 与标题。
- `spec_update` —— 一份规格的 frontmatter（字段与链接）。它不碰正文。
- `spec_delete` —— 移除一份规格。
- `spec_validate` —— 报告悬空链接、重复 id 与父节点环。

正文用普通的 `write`/`edit` 工具撰写与编辑；规格工具负责 frontmatter 与结构。

## 使用规格（Working with specs）

1. **当规格管辖这项工作时先定位。** 从一个已知的根或你正在触碰的模块出发，用 `spec_graph` 看邻域、
   用 `spec_get` 看某个节点的元数据、用 `read` 看它的正文。用 `spec_grep` 按内容查找规格。
2. **对齐。** 把改动与规格记录的决策和契约调和；在背离之前先暴露矛盾。
3. **更新。** 当改动改变了边界、契约或决策时，更新规格 —— 用 `spec_update` 改 frontmatter
   （包括 `status`），用 `edit` 改正文 —— 并为新模块用 `spec_create` 新建。
4. **检查。** 结构改动之后运行 `spec_validate`。
